# Инструкция для Claude — работа с сайтом adorelanguages.com

Этот файл — памятка на случай, если новая сессия Claude ничего не помнит о предыдущей работе.
Прочитай его целиком перед тем, как что-то менять в репозитории. Если что-то в реальном коде
разошлось с этим описанием — доверяй коду, а не файлу, и обнови файл заодно.

## Что это за проект

Статический сайт (GitHub Pages, кастомный домен через CNAME → adorelanguages.com), блог
"Обожаю Языки" — посты про этимологию, идиомы, бренды и лингвистические факты. У Вадима также
есть тот же контент в Facebook (fb) и на сайте (site) — это два параллельных каталога.

Ключевая особенность блога: **весь содержательный текст — на картинках** (посты — это готовые
карточки с текстом, нарисованные заранее). На страницах сайта НЕТ и не должно быть видимого
текста-дублёра — только картинка, теги (скрыты) и мета-данные для SEO. Исключение: у некоторых
старых постов есть собственные видимые комментарии автора под картинкой (`<ul class="bullets">`) —
их не трогать и не добавлять новые по своей инициативе.

## Структура репозитория

- `index.html` — главная страница сайта (adorelanguages.com), с большой картинкой собаки,
  круглой кнопкой «Поиск» и ссылками на ФБ/сайт/Instagram/Telegram.
- `fb/<slug>/index.html` — просто редирект (`meta http-equiv="refresh"`) на конкретный пост в Facebook.
- `site/<slug>/index.html` — полноценная страница поста: картинка, мета-теги, JSON-LD, блок разделов, теги.
- `images/posts/<slug>.png` — картинка поста (обычно 756×756).
- `links/fb/posts.json` — каталог постов для ФБ (slug, title, tags).
- `links/site/posts.json` — тот же список + поле `"bg"` (см. ниже про цвета).
- `links/site/sections.json` — какие посты входят в какие разделы.
- `links/site/section/<key>/index.html` — страница одного раздела.
- `links/site/all/index.html`, `links/fb/all/index.html` — общая лента всех постов.
- `links/site/index.html` — страница поиска по тегам/названию + список всех разделов.
- `scripts/generate_sitemap.py`, `scripts/ping_indexnow.py` — запускаются GitHub Action'ом
  (`.github/workflows/update-sitemap.yml`) автоматически при пуше в `links/site/posts.json` или
  `links/fb/posts.json` — **sitemap.xml обновлять руками не нужно**, бот сам закоммитит.

## Как добавить новый пост — пошагово

Вадим обычно присылает: заголовок, раздел(ы) (или «без раздела»), ссылку на пост в Facebook,
список тегов через `#`. Картинка обычно уже лежит в подключённой папке `Загрузки/посты` —
проверяй её первым делом (Glob по этой папке), имя файла = точное название поста + `.png`.

1. **Прочитать картинку** (инструмент Read) — это единственный источник текста поста.
2. **Определить bg** — открыть картинку через PIL, взять цвет пикселя `(5,5)`:
   - `pink`  ≈ rgb(245, 220, 207)
   - `lilac` ≈ rgb(233, 206, 242)
   - `blue`  ≈ rgb(70, 19, 89)   ← это тёмно-фиолетовый на вид, но в системе Вадима это «синий»!
   - `green` ≈ rgb(240, 247, 205)
   Bg обязан быть одним из этих четырёх значений — это bucket для JS-шаффла на страницах каталога
   (см. `links/site/all/index.html` — цикл pink → lilac → blue → green, все посты внутри бакета
   перемешиваются случайно при каждой загрузке страницы, порядок цветов не меняется никогда).
3. **Сгенерировать slug** — транслитерация заголовка, без пробелов и разделителей, всё слитно
   строчными буквами (например «Диванная картошка» → `divannayakartoshka`, «Цветная собака» →
   `tsvetnayasobaka`). Если Вадим сам не даёт slug — генерируй сам по этому правилу.
4. **Проверить дубликаты** — прогнать по `links/fb/posts.json` и `links/site/posts.json`, что
   такого slug/title ещё нет.
5. **Написать тексты**:
   - Полное описание (для `meta name="description"` и JSON-LD `"description"`, должны совпадать
     дословно) — переписать всё содержание карточки в связный текст, обычно начиная с
     «НАЗВАНИЕ ЗАГЛАВНЫМИ. Первая фраза...».
   - Короткая версия (для `og:description` и `twitter:description`, они между собой совпадают, но
     ОТЛИЧАЮТСЯ от полного описания) — один цепляющий заголовок-крючок в одно предложение.
   - Alt-текст картинки — «Название — краткая суть поста».
6. **JSON-LD keywords** = теги ровно как дал Вадим (ничего не добавлять от себя!) + всегда
   фиксированный хвост: `, обожаюязыки, обожаюязыкознание, языкознание, лингвистика, переводчики,
   иностранныеязыки, полиглот, филология, наукаоязыке`.
7. **Добавить записи** в конец массивов `links/fb/posts.json` (slug, title, tags) и
   `links/site/posts.json` (slug, title, tags, bg) — редактировать через `json.load`/`json.dump`
   с `indent=2, ensure_ascii=False` (это уже совпадает с текущим форматированием файлов, диффы
   получаются минимальные). **Если Вадим прислал пост «пока без ссылки на ФБ»** — пропустить только
   этот пункт для `links/fb/posts.json` (и пункт 8 про `fb/<slug>/index.html` целиком), но
   `links/site/posts.json` и всё остальное (site-страницу, sections.json, картинку) всё равно
   добавлять полностью. Когда Вадим позже пришлёт ссылку на Facebook — досоздать `fb/<slug>/index.html`
   по обычному шаблону (шаг 8) и дописать запись в `links/fb/posts.json` (шаг 7), больше ничего
   пересоздавать не надо.
8. **Создать `fb/<slug>/index.html`** — короткий редирект на присланную ссылку Facebook (шаблон
   ниже).
9. **Создать `site/<slug>/index.html`** — по шаблону (ниже). Блок разделов:
   - Если раздел один — `<p class="related-title">Раздел:</p>` и один `<li>`.
   - Если разделов два и больше — `<p class="related-title">Разделы:</p>` и по `<li>` на каждый.
   - Если без раздела — весь `<!--SECTIONS--> ... </div>` блок просто не добавлять (сразу от
     картинки к `.toggle`).
   - Для идиом с языком — ссылка вида `/links/site/section/idiomy/?lang=<язык>`, текст
     «Идиомы: <язык>».
   - Для раздела «Языки» (`yazyki`) с конкретным языком — так же, но `/links/site/section/yazyki/?lang=<язык>`,
     текст «Языки: <язык>» (у `yazyki`, как и у `idiomy`, в `sections.json` объект `languages`, а не
     плоский `slugs` — см. пункт 10). Пост может состоять сразу в разделе `yazyki` по нескольким языкам —
     тогда один `<li>` на каждый язык.
10. **Обновить `links/site/sections.json`**, если пост относится к разделу(ам)** — для «простых»
    разделов (`brendy`, `osobyeslova`, `strany`, `etimologiya`, `illyustraciiayu`, `lingvistika`,
    `igraslov`, `zagadki`, `toponimy`) добавить slug в их `"slugs"` массив; для `idiomy` и `yazyki`
    (у обоих объект `"languages"`, а не `"slugs"`) добавить slug в массив нужного языка —
    `<раздел>.languages.<язык>`, создав ключ языка, если его ещё нет. Редактировать точечной заменой
    строки по номеру строки (не пересобирать весь JSON целиком) — там компактный однострочный формат
    массивов, и одинаковые названия языков встречаются в ДВУХ разных объектах (`idiomy.languages` и
    `yazyki.languages`) на разных строках файла — искать по номеру строки, а не только по тексту
    `"<язык>":`, иначе легко попасть не в тот раздел.
11. **Скопировать картинку** в `images/posts/<slug>.png`.
12. **Закоммитить и запушить** (см. раздел про git ниже).

Если нужно создать **новый раздел** — добавить ключ в `sections.json`, скопировать
`links/site/section/strany/index.html` как шаблон (это «простой» раздел без языкового фильтра) и
заменить 4 вхождения: `<title>`, `<h1 id="title">`, `sections['strany']` → `sections['ключ']`,
и строку `` `Страны (${posts.length})` ``. Добавить ссылку на раздел в `links/site/index.html` в
блок `.sections`, подобрав следующий цвет по кругу: `#F4DBCE` (персиковый) → `#E9CEF2` (сиреневый)
→ `#461359` с `color:rgb(129,239,135)` (тёмный, светло-зелёный текст) → `#F0F7CD` (светло-зелёный)
→ по кругу.

## Шаблон `site/<slug>/index.html`

Проще всего скопировать структуру любого недавнего поста (например `site/morgenmuffel/index.html`
или `site/trampova/index.html`) и заменить: title, meta description, og/twitter title+description,
JSON-LD (headline/description/keywords/url), путь к картинке, alt, блок `.related` (или его
отсутствие), список тегов в `.tags`. CSS-блок в `<style>` у всех "простых" постов одинаковый —
копировать один в один. **Не забыть также блок звезды «Добавить этот пост в любимые посты»** (`.top-row`
CSS + HTML-кнопка `.hitlist-btn` + `<script>` перед `</body>` с `POST_TITLE`) — см. раздел «Звезда
„Добавить этот пост в любимые посты“» ниже, самый чистый пример для копирования — `site/kak-dela/index.html`.

## Правила, которые легко забыть

- **Никогда не добавлять видимый текст на страницы постов** — это специально нарушает концепцию
  блога (текст только на картинках). Скрытый на 100% текст (`display:none` без возможности
  раскрыть) тоже решили не делать — обсуждали риски с точки зрения политик Google по скрытому
  контенту, да и не решает реальную причину непроиндексированных страниц (см. ниже). Единственный
  согласованный инструмент SEO — meta description + JSON-LD + короткое summary для og/twitter.
- Теги в `.tags` и в `posts.json` — **ровно то, что прислал Вадим**, без отсебятины. Единственное
  дополнение, которое можно делать автоматически — фиксированный хвост в JSON-LD keywords (см. п.6).
- Раздел/Разделы — строго по числу `<li>` (проверять после любого добавления второго раздела
  существующему посту).
- bg — только 4 строго фиксированных значения, определять по реальному цвету пикселя, а не на глаз.
- Слаг — транслитерация без разделителей, слитно.
- **Фарси / персидский — это один и тот же язык под двумя названиями.** Если пост относится к
  этому языку (в разделе «Языки» и/или «Идиомы»), всегда добавлять ОБА ключа — `"фарси": [...]`
  и `"персидский": [...]` — в соответствующий `languages` объект в `sections.json`, оба со
  slug'ом этого поста. В блоке `.related` на странице поста писать одну строку на раздел вида
  «Языки: фарси / персидский» (или «Идиомы: фарси / персидский»), ссылка при этом ведёт на
  `?lang=фарси` (неважно на какой из двух — раздел покажет тот же список постов). Если для
  какого-то из двух разделов есть только одна из привязок — это баг, найденный и исправленный один
  раз (пост `lyuboviorgany`) — проверять оба раздела сразу, когда добавляешь этот язык.
- **Тот же приём для других языков с альтернативными названиями** — например адыгский / черкесский
  (пост `kak-dela`). Всегда добавлять оба ключа-названия в `languages` с одним и тем же slug'ом,
  а в `.related` писать одну строку вида «Языки: адыгский / черкесский», ссылка на `?lang=<любое
  из двух>`. Список таких known-пар языков: фарси/персидский, адыгский/черкесский,
  нидерландский/голландский (пост `dikiiobraz`) — если появится ещё одна пара синонимичных
  названий, добавлять её сюда же.
- Перед пушем — `git pull`, потому что бот `sitemap-bot` может успеть закоммитить
  `sitemap.xml`/`.indexnow_state.json` между сессиями.

## Git / деплой

- Репозиторий: `github.com/adorelanguages/adorelanguages`, ветка `main`, деплой — GitHub Pages
  (классический branch-deploy, без своего workflow для Pages).
- Клонировать в `/tmp` (не в примонтированную `outputs`-папку — там git ломается на спец-файлах
  вроде `.git/config.lock`, монтированная файловая система их не поддерживает).
- Для пуша нужен GitHub Personal Access Token от Вадима (он присылает его в чат по запросу).
  Использовать так, не логируя токен в вывод:
  ```
  git push "https://x-access-token:${GITHUB_TOKEN}@github.com/adorelanguages/adorelanguages.git" HEAD:main
  ```
- Если токен уже был один раз использован и отправлен в чат открытым текстом — стоит посоветовать
  Вадиму отозвать/перевыпустить его после завершения задачи (это разовая гигиена, не запрет).
- Картинки постов Вадим кладёт в подключённую папку `Загрузки/посты` (Downloads/посты) на его
  компьютере — она видна через Read/Glob по пути `C:\Users\vadim\Downloads\посты`, а в bash-песочнице
  как `/sessions/.../mnt/посты/`.

## Разное, что уже обсуждали и решили

- **Cowork не хранит память между обычными сессиями** (это открыто признанное ограничение beta на
  момент этого разговора) — только внутри Project. Этот файл — способ обойти это ограничение для
  работы над сайтом конкретно.
- **SEO / индексация в Google**: главная причина непроиндексированных страниц у Вадима —
  «Discovered — currently not indexed» (Google ещё не дошёл до крауления, это про приоритет для
  нового домена, а не про качество контента) — «Crawled — currently not indexed» (реально про
  тонкий контент) была у него лишь на паре страниц. Хэштеги/тонкий контент — не главная проблема,
  решать её добавлением видимого текста не будем (см. правила выше).
- **Мобильная адаптивность**: если Вадим присылает скриншоты «сайт выглядит по-разному на разных
  айфонах» — сначала проверь, не связано ли это с настройками конкретного устройства (Safari
  Page Zoom для сайта, или Настройки → Экран и яркость → Вид → Стандарт/Увеличенный), а не сразу
  чини вёрстку — в прошлый раз разница объяснялась именно этим, а не багом кода.
- Стандартные цвета интерфейса сайта: основной текст/навигация `rgb(45, 44, 91)`, шрифт — кастомный
  `Factora` (файлы `FACTORA-*.OTF` в корне репозитория).
- **Знак ударения (´) в тексте постов.** Шрифт `Factora` (см. `FACTORA-*.OTF`) НЕ содержит глиф для
  объединяющего Unicode-символа U+0301 (combining acute accent) — если вставить его прямо в текст (как
  в исходном тексте от Вадима вида «ду́шить»), браузер молча подставляет резервный шрифт только для
  этого символа, а соседние буквы остаются в Factora — из-за разной ширины символов между шрифтами
  возникает заметный лишний зазор (проверено на посте `voodushevlenie`, воспроизводилось что с явным
  `font-family: Georgia` для этого символа, что без него — Georgia на Windows тоже ненадёжно сочетает
  этот знак с кириллицей). Факт отсутствия глифа проверяется так: `fontTools.ttLib.TTFont(...).getBestCmap()`,
  `0x0301 in cmap`. **Рабочее решение** — НЕ использовать U+0301 вообще, а брать обычный неприсоединяемый
  символ ´ (U+00B4, ACUTE ACCENT) — он в Factora есть — и позиционировать его чисто через CSS, без
  зависимости от способности шрифта сочетать диакритику:
  ```html
  <span style="position:relative; display:inline-block;">у<span style="position:absolute; top:-0.55em; left:0; right:0; text-align:center; font-size:0.6em; line-height:1;">´</span></span>
  ```
  (пример для буквы «у» — подставлять нужную гласную вместо неё внутри обеих пар `<span>`). Копировать
  этот паттерн один в один при следующем посте, где Вадим прислал текст со знаком ударения.
- **Тире**: Вадим не любит длинное тире (—), даже там, где оно стандартно. Везде используем короткое
  тире (–), не дефис (-). Это касается и текста постов, и служебных сообщений на страницах (например,
  пустых состояний на страницах голосований).
- **Страницы голосований** (`/golosovania/<slug>/` и старая `/idei/`): пустое состояние списка вариантов
  должно звучать как «Пока нет одобренных вариантов – стань первым, кто предложит свой!» — короткое
  тире, «стань» (не «станьте»). Соблюдать в любых новых страницах голосований.
- **Статус модерации в Google Таблице — чекбоксы, не текст.** Столбец C (status) в каждом листе
  голосования — это чекбокс (TRUE/FALSE), не текст «approved»/«pending». Скрипт читает `r[2] === true`
  и пишет `false` при новой заявке. При создании листа для нового голосования — дублируй существующий
  лист, где уже стоят чекбоксы (например, «odnimslovom»), а не создавай новый лист с нуля, чтобы формат
  скопировался автоматически.
- **Пост, к которому привязано голосование** (например `site/odnimslovom/`), получает поверх обычного
  шаблона поста ДВЕ вещи: розовую пульсирующую кнопку `Голосовать →` (класс `.vote-cta`, цвет
  `rgb(244,219,206)`, бегущая пунктирная рамка через SVG с JS-вычислением размера в пикселях — см.
  `site/odnimslovom/index.html` как образец) сразу под картинкой поста, и пункт в блоке `.related` вида
  «Раздел: Голосования» (текст ссылки — «Голосования», заголовок блока — «Раздел:»/«Разделы:» по общему
  правилу, если у поста есть и другие разделы) со ссылкой на `/golosovania/<slug>/`. Всё остальное на
  странице поста — без изменений, по обычному шаблону (см. раздел «Шаблон site/<slug>/index.html» выше).
- **Страница `/links/site/`** (поиск по постам) — под рядом цветных кнопок разделов (`.sections`)
  есть отдельная розовая кнопка `Голосования →` в том же стиле `.vote-cta`, ведущая на `/golosovania/`.
  Она не часть `.sections` и не привязана к `sections.json` — это отдельный статичный блок
  `.vote-cta-row` в конце страницы.
- **Защита от дублей в голосованиях — НЕ универсальна, настраивается по каждому голосованию, и есть
  ТРИ режима.** `doPost` при `action: 'submit'` всегда сначала ищет текст новой заявки (без учёта
  регистра и пробелов) среди ВСЕХ существующих строк (и pending, и approved) в том же листе. Дальше —
  в зависимости от режима:
  1. **По умолчанию (дедуп включён)** — совпадение возвращает `{ ok: false, error: 'duplicate' }`,
     новая строка не создаётся. Фронтенд показывает «Такой вариант/идея уже есть в списке!». Пример:
     «Одним словом» (одно и то же слово от разных людей — ошибка, схлопывать).
  2. **`NO_DEDUP_POLLS`** (массив slug'ов в Apps Script) — дедуп ОТКЛЮЧЕН, совпадение просто добавляет
     ещё одну отдельную строку с 0 голосов. Пока не используется ни одним голосованием на практике
     (карта читателей идёт через отдельный `action`, см. ниже, а не через этот массив).
  3. **`MERGE_VOTE_ON_DUPLICATE_POLLS`** (массив slug'ов в Apps Script) — совпадение НЕ создаёт новую
     строку и не возвращает ошибку, а сразу прибавляет +1 голос к уже существующей строке с этим
     текстом и возвращает `{ ok: true, merged: true, votes: N }`. Новая (первая) заявка при этом сразу
     получает 1 голос (не 0) — сама отправка формы уже считается голосом. Фронтенд на `merged: true`
     показывает не «отправлено на модерацию», а «этот вариант уже предлагали – голос добавлен».
     Используется в «Любимых постах» (см. ниже, URL/slug остался `hitlist`) — там сама суть в подсчёте голосов за пост, и заявка
     читателя B с тем же названием поста, что уже предложил читатель A, обязана прибавить голос
     посту A, а не создать вторую параллельную строку или быть отклонённой.
  **При создании КАЖДОГО нового голосования — всегда спрашивать Вадима, какой из трёх режимов нужен,
  прежде чем публиковать его.** Карта читателей — отдельный случай: она в любом случае идёт через свои
  собственные `action` (`submit_location`/`get_locations`), не через дедуп-проверяемый `action: 'submit'`
  вообще (см. правило ниже про карту), но сам вопрос «какой режим дублей нужен» всё равно стоит явно
  проговаривать для любого нового голосования на общей инфраструктуре `submit`/`poll`.
- **Порядок голосований на `/golosovania/`.** Три перманентных пункта жёстко закодированы первыми
  блоками на странице (не часть массива `POLLS`), в этом порядке:
  1. «Карта читателей» (`/golosovania/karta/`) — самый первый пункт.
  2. «Любимые посты» (`/golosovania/hitlist/` — URL и slug не переименовывали) — второй пункт.
  3. «Идеи для постов» (`/golosovania/idei/`) — третий пункт.
  Все остальные голосования идут под ними (массив `POLLS`), отсортированные по дате публикации на
  сайте: самое свежее — сразу после «Идей для постов», самое старое — в самом низу. На практике это
  значит: когда добавляешь новое голосование в массив `POLLS` в `golosovania/index.html`, вставляй его
  объект В НАЧАЛО массива (а не в конец), чтобы порядок рендеринга соответствовал «новое сверху, старое
  снизу». Эти три перманентных пункта в массив `POLLS` никогда не входят — они всегда остаются первыми
  тремя хардкоженными блоками.
- **Кнопка «наверх страницы» (`.to-top`) — обязательный элемент шаблона любой страницы голосования**
  (и вообще любой длинной листинговой страницы сайта — уже стоит на всех страницах разделов в
  `links/site/section/`, а также на `links/site/all/`, `links/fb/all/`). Стандартный набор: CSS-блок
  `.to-top`/`.to-top.visible` перед `</style>`, `<a href="#" class="to-top" id="to-top" aria-label="Наверх">↑</a>`
  сразу после закрытия `.wrap`-обёртки (перед `.lightbox-overlay`), и отдельный `<script>` перед `</body>`:
  обработчик `scroll` (показывает кнопку при `window.scrollY > 300`), функция `scrollToTop(e)`
  (`e.preventDefault()` + `scrollTo({top:0, behavior:'smooth'})`), повешенная и на `click`, и на
  `touchend` (второе — подстраховка от задержки/неоднозначности тапа на мобильных, отдельно от
  описанного ниже бага с двойным тапом).
  **Важно про показ/скрытие кнопки — НЕ через `pointer-events: none/auto`.** Раньше кнопка скрывалась
  через `opacity: 0` + `pointer-events: none`, что на iOS Safari надёжно вызывало баг «нужен двойной
  тап»: первый тап по только что появившейся кнопке (сразу после остановки скролла) не долетал до неё —
  видимо, WebKit не успевал применить `pointer-events: auto` синхронно с переключением класса `.visible`
  во время скролл-инерции, и хит-тестинг ещё «видел» старое значение `none`; только второй тап (когда
  отрисовка уже точно догнала класс) срабатывал. Воспроизводилось даже на страницах без единого текстового
  поля (например `links/site/all/`), значит дело не в фокусе/клавиатуре, а именно в этом. Исправили
  переходом на чисто позиционное скрытие: `pointer-events` больше не трогаем вообще (кнопка всегда
  кликабельна), а в скрытом состоянии просто уводим её за пределы клика через больший `transform:
  translateY(90px)` (вместо прежних `8px`) — кнопка физически уезжает из-под пальца, а не остаётся на
  месте с отключённым `pointer-events`. Если этот баг с двойным тапом когда-нибудь всплывёт снова на
  новой странице — не трогать JS (`click`/`touchend`), проверять именно этот CSS-паттерн (не возвращать
  `pointer-events: none/auto` в `.to-top`/`.to-top.visible`).
  Копировать блок один в один из любой страницы, где уже есть (например `golosovania/karta/index.html`
  или `links/site/all/index.html`). При создании НОВОЙ страницы голосования — добавлять сразу, не
  дожидаясь отдельной просьбы.

## Любимые посты (`/golosovania/hitlist/`)

Назывался раньше «Хит-лист» — переименовали видимый текст в «Любимые посты», но URL/slug
`hitlist`, `POLL_ID`, название вкладки в таблице и все внутренние идентификаторы в
`Code.gs` остались как есть (никаких причин их менять не было, только косметика на сайте).

Голосование за самый понравившийся пост блога. Топ-3 по количеству голосов отмечены золотой/
серебряной/бронзовой круглой плашкой с цифрой перед названием поста (`.rank-badge`, классы
`.gold`/`.silver`/`.bronze`).

**Как голосуют читатели — два независимых канала:**

1. **Кнопка 👍 в уже показанном списке** на самой странице `/golosovania/hitlist/` — работает как
   обычно, +1 голос за клик.
2. **Звезда «Добавить этот пост в любимые посты» на странице каждого поста** (`site/<slug>/index.html`,
   блок `.top-row` рядом с кнопкой «На главную», см. следующий раздел). Это единственный способ
   ВПЕРВЫЕ добавить пост в список — свободного текстового поля для этого больше нет
   (было раньше, убрали). Вместо него на `/golosovania/hitlist/` теперь стоит **поиск постов**
   (тот же `posts.json`, что и на `/links/site/`, поиск по названию/тегам) — результаты ведут
   прямо на страницу нужного поста, а голосовать читатель может уже там, звездой.

**Почему так:** свободный текст в форме требовал модерации (кто угодно мог вписать мусор). Звезда на
странице поста жёстко привязана к реальному названию поста (задано кодом страницы, читатель ничего
не вводит) — подделать нечего, поэтому такие голоса публикуются сразу, без модерации.

**Механика на сервере (`Code.gs`) — два action, оба ведут в одну и ту же логику дублей/слияния:**
- `submit` — из бывшего текстового поля (сейчас нигде на сайте не используется, но код оставлен на
  случай, если понадобится снова); требует модерации (`approved = false` при первой заявке).
- `vote_post` — со звезды на странице поста; публикуется сразу (`approved = true`), email-уведомление
  о модерации не шлётся. Если голос пришёл на уже существующее, но ещё не одобренное название (кто-то
  успел вписать его вручную до того, как убрали форму) — запись одобряется автоматически.

Оба action используют общий режим дублей `MERGE_VOTE_ON_DUPLICATE_POLLS` (см. правило про три режима
дублей выше): повторная заявка с тем же названием поста не создаёт вторую строку и не отклоняется как
«дубликат», а сразу прибавляет +1 к уже существующей. Первая (новая) заявка сразу получает 1 голос —
сама отправка уже засчитывается как голос за пост.

Миниатюра — `/images/posts/hitlist.png` (подиум 1-2-3 места, монохромный тёмно-синий `rgb(45,44,91)`,
фон — стандартный зелёный `rgb(240,247,205)`).

## Звезда «Добавить этот пост в любимые посты» на страницах постов

Каждая страница `site/<slug>/index.html` содержит кнопку-звезду, которая одним кликом голосует за этот
пост в Любимых постах (см. выше) и сразу переносит читателя на `/golosovania/hitlist/`, где видно и его
голос, и все остальные предложенные посты.

**При добавлении НОВОГО поста этот блок обязателен** — копировать один в один из любого недавнего
поста (например `site/kak-dela/index.html`) вместе с остальным CSS/HTML:

- В `<style>`: правила `.top-row`, `.hitlist-btn` (и `.hitlist-btn:hover`, `.hitlist-btn .star`,
  `.hitlist-btn .star-2`, `@keyframes star-blink`, `.hitlist-btn.sending`, `.hitlist-btn.voted`,
  `.hitlist-btn.voted .star`). Существующее правило `.back` теряет `margin-bottom: 20px` (перенесён
  на `.top-row`).
- В `<body>`: кнопка `.back` оборачивается в `<div class="top-row">` вместе с новой кнопкой
  `<a class="hitlist-btn" href="#" id="hitlist-btn">` (звезда-текст-звезда, `#9733;` дважды).
- Перед `</body>`: отдельный `<script>` с самовызывающейся функцией — внутри задаётся
  `POST_TITLE = "<точное название поста, как в posts.json>"` (обязательно то же самое, что в
  `links/site/posts.json`, иначе голоса за один и тот же пост разъедутся по двум разным строкам в
  таблице). `API_URL` — тот же адрес Apps Script, что и везде.
- Переход на `/golosovania/hitlist/` после клика происходит **синхронно**, до ответа сервера (сам
  POST-запрос уходит с `fetch(..., { keepalive: true })`) — это специально, потому что мобильные
  браузеры блокируют `window.location.href`, если он вызван уже после того, как асинхронный fetch
  завершился (жест пользователя к этому моменту как бы «устарел»).
- Голос запоминается в `localStorage` (`adore_hitlist_voted_posts`, массив названий постов) — второй
  клик с того же браузера по тому же посту невозможен, кнопка сразу показывает «Уже в любимых постах!».

## Карта читателей (`/golosovania/karta/`)

Идея Вадима: карта мира на сайте, где закрашены страны, откуда есть читатели (читатели сами отмечают
страну+город через форму). Клик по закрашенной стране — увеличенный силуэт этой страны и список
городов рядом, с количеством читателей в каждом.

Решения, принятые по этой фиче:
- **Формат — плоская 2D-карта**, не 3D-глобус.
- **Размещение — через `/golosovania/`**, а не отдельный раздел сайта.
- **Порядок на `/golosovania/` — «Карта читателей» первым перманентным пунктом**, «Идеи для постов»
  вторым (см. правило про порядок голосований выше). Карта важнее идей для Вадима.
- **Без модерации.** Отметки страна+город появляются на карте сразу, никто их не проверяет вручную
  (в отличие от голосований с текстовыми предложениями).
- **Дубли — обязательны и нужны.** Один и тот же город от разных читателей должен увеличивать счётчик,
  а не блокироваться. Поэтому карта работает через СВОИ отдельные `action` в Apps Script
  (`submit_location` / `get_locations` — доступ через `?action=get_locations` в GET и
  `{ action: 'submit_location', country, city }` в POST), а НЕ через дедуп-проверяемый `action: 'submit'`
  от обычных голосований.

Технические детали реализации:
- **`maps/world.svg`** — карта из npm-пакета `@svg-maps/world` (256 стран/территорий, каждая —
  отдельный `<path>` с `id` = ISO alpha-2 код в нижнем регистре, например `id="ru"`, и
  `aria-label` = название на английском). **Лицензия CC BY 4.0** (автор Victor Cazanave,
  github.com/VictorCazanave/svg-maps) — атрибуция добавлена внизу страницы `/golosovania/karta/`
  (блок `.attribution`, ссылки на автора и на текст лицензии).
- **`maps/countries-ru.json`** — список всех 256 стран с русскими названиями для выпадающего списка
  (id + ru), сгенерирован через Python-библиотеку `babel` (`Locale('ru').territories`, офлайн, без
  обращения к интернету) с ручным дополнением 8 названий необитаемых островов/территорий, которых
  не было в данных Babel. Этот JSON вшит прямо в `golosovania/karta/index.html` (константа
  `COUNTRIES`), отдельного запроса за ним со страницы нет.
- **`golosovania/karta/index.html`** — страница с формой (выбор страны из выпадающего списка + поле
  «город» + кнопка «Отметиться») и самой картой. Карта загружается через `fetch('/maps/world.svg')`
  и вставляется в DOM (`innerHTML`), затем каждой стране с читателями красится заливка (интенсивность
  зависит от количества читателей — `rgba(45,44,91, opacity)`, страны без читателей — светло-серые).
  Клик по закрашенной стране считает `path.getBBox()` и подгоняет `viewBox` SVG под неё (с отступом),
  показывает кнопку «← Ко всей карте» и панель со списком городов (отсортирован по убыванию количества
  читателей). Миниатюра `/images/posts/karta.png` (простая иконка глобуса с точками, сгенерирована,
  не фотография поста) используется и в шапке страницы (с лайтбоксом-увеличением, как на других
  страницах голосований), и как миниатюра в списке `/golosovania/`.
- **Apps Script** расширен: `LOCATIONS_SHEET = 'Locations'`, функции `submitLocation()` и
  `getLocations()`, роутинг в `doGet`/`doPost` по `action`. Использует общий helper `appendPollRow()`
  (тот же, что и голосования, — устойчив к чекбоксам/широким диапазонам форматирования).

**Единственное, что осталось сделать вручную в Google Таблице (не через код):**
1. Создать новую вкладку с названием ровно `Locations` в той же Google Таблице, где лежат вкладки
   `Ideas` и `odnimslovom`.
2. В строке 1 этой вкладки можно (не обязательно) подписать заголовки колонок для порядка: `id`,
   `country`, `city`, `timestamp` — сам Apps Script их не читает, ориентируется по номеру колонки
   (A=id, B=country, C=city, D=timestamp), но подписи помогают не запутаться при ручном просмотре.
3. Вставить обновлённый `Code.gs` (см. историю чата или запросить у ассистента) в редактор Apps Script
   и опубликовать новую версию того же деплоя (Bereitstellen → Bereitstellungen verwalten → карандаш →
   Neue Version → Bereitstellen — см. раздел «Git / деплой» ниже про механику German-locale UI).
4. Проверить: открыть `/golosovania/karta/`, отправить тестовую страну+город, обновить страницу и
   убедиться, что страна закрасилась и город появился в списке при клике.

**CSS-ловушка: нельзя «снять» text-decoration с дочернего элемента.** Если у родителя
(например, кнопки `.country-list-toggle`) стоит `text-decoration: underline`, то попытка убрать
подчёркивание с части текста через дочерний `<span style="text-decoration: none;">...</span>`
**не работает** — подчёркивание родителя всё равно прорисовывается под потомком (так рисуются
decoration lines в CSS, это не баг браузера). Единственный рабочий способ — развернуть логику
наоборот: убрать `text-decoration` с самого родителя и обернуть в `<span style="text-decoration:
underline;">` только тот фрагмент текста, который должен быть подчёркнут, оставив остальное как
обычный текст без обёртки. Так сделано в `golosovania/karta/index.html` для кнопки
«Список стран: N» — подчёркнуто только «Список стран», а «: N» и «Скрыть список стран» (когда
список открыт) собираются через `btn.innerHTML` с явным `<span style="text-decoration:
underline;">`.


**Верстка шапки страницы (thumb + h1 + home-button) может ломаться на мобильных при длинном
заголовке.** Стандартная шапка (`.topbar`: миниатюра-картинка слева + `<h1>` по центру + кнопка
«← На главную страницу» справа, flex-row) не резиновая по умолчанию — если заголовок содержит
длинное слово без пробелов (например, «Обожателей»), у флекс-элемента `h1` минимальная ширина
по умолчанию равна ширине этого слова (`min-width: auto`), и на узких экранах это может вытолкнуть
кнопку `.home-button` за пределы экрана (было с `/golosovania/karta/` после переименования в
«Карта Обожателей Языков»). ВАЖНО: при первой попытке чинить это я без спроса заодно уменьшил
шрифт заголовка и вид кнопки «На главную страницу» на мобильных — пользователь это отклонил,
сказал явно: размер шрифта заголовка и вид кнопки должны совпадать со всеми остальными
страницами, менять их без запроса нельзя. Правильный процесс в такой ситуации: предложить
варианты (например, уменьшить/убрать миниатюру-картинку слева), показать прототипы каждого
(скриншот через Claude in Chrome, БЕЗ пуша в прод) и дать пользователю выбрать — а не сразу
имплементировать свою идею. Финальное решение для карты (пользователь выбрал именно этот
вариант из двух прототипов): на `@media (max-width: 480px)` миниатюра-глобус (`.thumb-link`)
просто скрывается (`display: none`), а `h1` и `.home-button` остаются без изменений — так
кнопка помещается на экране, и ничего из того, что не просили менять, не меняется.

**Обновление (позже переигранное): иконка в шапке карты — не глобус, а «сердце в кружке».**
Миниатюра в шапке `/golosovania/karta/` и в списке `/golosovania/` больше не глобус
(`/images/posts/karta.png`), а новая иконка `/images/icons/serdce-sinee.png` (сиреневый кружок
`rgb(233,206,242)` с синим сплошным сердцем `rgb(70,19,89)` внутри, без обводки кружка) — тот же
файл используется и на десктопе, и на мобильных (единый `<img class="thumb">`, отдельный
`.mobile-badge` больше не нужен и был убран).
- **Белый квадрат вокруг кружка.** Класс `.thumb` изначально был `border-radius: 14px` (скруглённый
  квадрат) + `box-shadow` — при прозрачном PNG с кругом внутри это давало на карте видимый белый/
  прямоугольный «квадрат-рамку» вокруг кружка (box-shadow повторяет форму рамки элемента, а не
  формы непрозрачных пикселей внутри). Исправлено на `.thumb { border-radius: 50%; }` — теперь и
  обрезка картинки, и тень идут по кругу, квадрат исчезает. На странице `/golosovania/` у
  `.poll-thumb` эта рамка осталась намеренно (Вадим сказал, что там она не мешает, трогать не
  просил) — там свой отдельный CSS-класс, `.thumb` на карте это не затрагивает.
- **Размер на мобильных.** После объединения desktop/mobile-версий иконки в один элемент кнопка
  «На главную страницу» на мобильных снова обрезалась (иконка 96×96px слишком большая). Возврат к
  рабочему решению — `@media (max-width: 480px) { .thumb { width: 56px; height: 56px; } }` (те же
  56px, что раньше были у отдельного `.mobile-badge`), картинка при этом не прячется, просто меньше.

**Таблица стран/городов под картой — доп. правки (после первой волны правок выше):**
- Правый столбец «Обожателей Языков» сдвинут чуть левее (`.country-row .row-right { gap: 32px; }`
  вместо `8px`), левый заголовок «Страны и города» («города» на второй строке) отцентрован через
  `.country-list-header .col-country { text-align: center; }` — так же, как уже был отцентрован
  правый заголовок.
- Цифры в строчках городов (`.city-count`) выровнены строго под стрелками (`.chevron`) в строчках
  стран, а не под цифрой самой страны.
- Размер шрифта строк таблицы (`.country-row`, `.country-list-header`) поднят до `1.05em` — так же,
  как текст над таблицей (`.lead`); только строки городов (`.city-sublist li`) остались мельче
  специально.
- Разделительная линия между строками стран (`.country-row { border-bottom }`) пропадала при
  раскрытии списка городов — оказалось, дело не в рендеринге (проверено: жирная красная тестовая
  рамка отрисовывалась нормально даже при динамическом раскрытии), а в низком контрасте цвета
  (`rgb(230,229,240)` почти сливался с фоном панели `rgb(244,244,255)`). Исправлено на
  `rgba(45,44,91,0.18)`.
- Отдельно не хватало линии-разделителя МЕЖДУ последним городом раскрытого списка и следующей
  страной (`.city-sublist` не имел своего `border-bottom`) — добавлено
  `.city-sublist { border-bottom: 1px solid rgba(45,44,91,0.18); }` (тот же цвет, что у
  `.country-row`).
- `.country-row:last-of-type { border-bottom: none; }` — мёртвое правило, реально ничего не
  выбирает, т.к. между `.country-row` вклиниваются `.city-sublist` (тот же уровень вложенности,
  другой класс), а `:last-of-type` матчит по тегу, не по классу. Не тронуто, вне рамок задачи.

**Как проверять мобильную вёрстку через Claude in Chrome, если `resize_window` не работает.**
В некоторых средах `resize_window` возвращает «успех», но `window.innerWidth` фактически не
меняется (окно браузера не ужимается ниже текущего разрешения экрана) — то есть реального
мобильного вьюпорта через этот инструмент добиться не получилось. Обходной путь: через
`javascript_tool` внедрить временный `<style id="mobile-sim">`, который через `!important`
жёстко подставляет `.wrap { max-width: 375px !important; }` и все мобильные значения из
медиа-запроса — это не проверяет сам синтаксис `@media`, зато честно проверяет, влезает ли
верстка в 375px по факту (через `element.getBoundingClientRect()` — сравнить `right` кнопки
и `right` `.wrap`, они должны совпадать, если переполнения нет). Такой временный стиль не
коммитится, существует только в текущей вкладке до перезагрузки страницы.


## Обсуждаемая, но НЕ реализованная идея: точки/бейджи читателей на карте страны

Статус на момент записи: это чистое обсуждение и прототипирование, НИЧЕГО из этого раздела
не задеплоено на сайт. Все прототипы делались временными правками прямо в живой вкладке
браузера (через инъекцию JS/CSS поверх `/golosovania/karta/`) и нигде не сохранялись —
если продолжать эту тему в новой сессии, всё придётся прототипировать заново, но сам ход
рассуждений и выводы ниже помогут не переоткрывать те же грабли.

**Отправная идея и почему её отложили.** Вадим хотел, чтобы города читателей наносились на
карту точками (сейчас страна просто закрашивается тем сильнее, чем больше читателей — без
разбивки по городам визуально). Решили пока этого не делать («Пока обойдёмся без городов на
карте»), потому что для этого нужны координаты городов, а сейчас в Google-таблице (вкладка
`Locations`) хранится только текст «страна + город», введённый читателем вручную — без
координат. Обсуждали два пути получить координаты:
1. Геокодировать текст города через внешний сервис (Nominatim/OpenStreetMap) прямо в Apps
   Script при отправке формы. Минусы: лишняя задержка при отправке (доля секунды — пара
   секунд), риск недоступности стороннего сервиса, и главное — риск ТИХИХ неверных совпадений
   (одноимённые города в разных странах, опечатки), которые в отличие от текущей текстовой
   правки почти невозможно заметить на глаз в таблице с одними координатами.
2. Дать читателю самому кликнуть точку на карте вместо/вместе с вводом текста, используя уже
   существующий зум карты на страну (см. `showCountry()` в `golosovania/karta/index.html`).
   Плюс — не нужен внешний сервис. Точность зависит от масштаба клика (после зума на страну
   клик пальцем попадает в среднем в пределах нескольких км). Прототип такого клика лежит у
   Вадима в папке — `klik_po_karte_prototip.html` (можно открыть прямо в браузере, карта и
   логика зума вшиты внутрь файла, полностью автономный).

**Идея, на которой в итоге остановились обсуждать дальше: не точки городов, а один бейдж на
страну.** Вместо множества точек — при клике на закрашенную страну (у которой есть хотя бы
один читатель) прямо на силуэте появляется ОДИН кружок с сердечком (тот же дизайн, что и
сиреневый кружок с синим сердцем в шапке мобильной версии карты, см. `images/icons/serdce-sinee.png`)
с белой цифрой внутри — общим числом читателей этой страны. Клик по кружку должен прокручивать
страницу к таблице стран/городов ниже. Договорились: кружок только ОДИН, только у той страны,
по которой кликнули (не показывать сразу для всех закрашенных стран — иначе близко
расположенные страны с читателями, например Германия/Польша, накладывались бы друг на друга).

**Открытый вопрос, который ещё не решили:** сейчас клик по стране уже сам по себе зумит карту
И открывает+прокручивает список городов (см. `showCountry()`). Если клик по кружку тоже должен
прокручивать к таблице — это дублирует/конфликтует с текущим поведением. Нужно решить: клик по
стране продолжает всё делать как сейчас (зум + бейдж), а прокрутка к таблице остаётся только
на кружке (то есть один клик по стране больше НЕ прокручивает автоматически, только зумит и
показывает бейдж) — или оставить всё как есть и клик по кружку добавить как ДОПОЛНИТЕЛЬНЫЙ
быстрый способ, не убирая автопрокрутку при клике на страну. Не выбрано.

**Главная техническая проблема места бейджа: центр bbox страны часто мимо.** Первая идея —
ставить кружок в геометрический центр `path.getBBox()` страны (тот же расчёт, что уже
используется для зума). Проверили это по-настоящему (не на глаз): для каждой страны взяли
центр bbox и проверили через `path.isPointInFill(point)` — попадает ли эта точка реально
внутрь силуэта страны. Провалились: Чили (центр — в открытом океане), Норвегия (центр — на
территории Швеции), Хорватия (центр — в Боснии и Герцеговине, которую хорватский полумесяц
огибает), Канада (видимо, из-за арктических островов, растягивающих bbox). Прошли проверку:
Франция, Россия, Япония, Италия. Причина — зум решает проблему «страна слишком маленькая», но
НЕ решает проблему «страна слишком узкая/вогнутая», потому что зум не меняет пропорции формы.

**Второй заход — вместо центра bbox использовать координаты столицы страны.** Идея Вадима,
и она работает значительно лучше геометрического центра именно потому, что столица почти
всегда осознанно выбрана внутри страны, в стороне от границ. У метода нет готовой формулы
перевода реальных широта/долгота в координаты именно этой SVG-карты (`maps/world.svg` из
пакета `@svg-maps/world`, viewBox `0 0 1010 666` — не 2:1, то есть не банальный equirectangular
на полный диапазон широт, проекция не подтверждена точной формулой). Поэтому координаты столиц
не вычислялись по формуле, а подбирались ПРАКТИЧЕСКИ и проверялись по-настоящему:
1. Взять свою географическую прикидку «примерно где по стране столица» как долю (fx, fy) от
   bbox страны (например, Осло — юго-восток Норвегии → fx≈0.25, fy≈0.85).
2. Автоматическим поиском по сетке рядом с этой точкой найти реальную точку на суше (проверено
   `isPointInFill`) с максимальным запасом от границ (clearance — считается сэмплингом
   расстояния до края в 12 направлениях), а не просто ближайшую подходящую.
   ВАЖНО: при таком поиске нельзя резать `d`-атрибут пути на подпути (по `M`/`m`) и мерить
   bbox каждого куска по отдельности, чтобy найти "материк" среди островов — относительные
   команды (`m`, строчная) в SVG-путях зависят от текущей точки, унаследованной от ПРЕДЫДУЩИХ
   команд в исходном пути; если вырезать кусок пути и вставить его в новый `<path>` отдельно,
   абсолютные координаты этого куска посчитаются неверно (проверено на Норвегии — «материк»
   как отдельный подпуть получил bbox `x=-58`, полная бессмыслица). Рабочий способ — всегда
   гонять `isPointInFill` на ПОЛНОМ оригинальном `<path>` элементе (это всегда верно, не зависит
   от relative/absolute багов), а не пытаться разбить его на части.
   Проверено этим методом на 4 проблемных странах: Норвегия и Хорватия и Канада теперь чётко
   попадают на свою территорию (Осло — на норвежском берегу, а не в Швеции; Загреб — на севере
   Хорватии, а не в Боснии; Оттава — рядом с реальной Оттавой, а не в пустых арктических
   островах). Чили — тоже стало сильно лучше (кружок на прибрежной полосе, а не в океане), но
   даже лучшая найденная точка имеет запас (clearance≈6.5) меньше, чем нужный радиус кружка
   (≈8.6) — то есть кружок будет слегка задевать океан по бокам чисто из-за того, что
   материковая часть Чили в этом месте физически уже, чем стандартный размер кружка. Для таких
   экстремально узких стран (Чили, вероятно и другие вроде Гамбии) кружок придётся либо
   делать индивидуально меньше, либо смириться с небольшим наездом на воду.
   Скриншоты всех 4 проверенных стран (у Вадима в папке): `capital_chile.jpg`,
   `capital_norway.jpg`, `capital_croatia.jpg`, `capital_canada.png`. Для сравнения «хороший
   случай» — `ok_france.png` (центр bbox отлично работает без всякой доп. логики).

**Не решено и не сделано:**
- Таблица координат столиц пока посчитана и проверена только для 4 стран (Чили, Норвегия,
  Хорватия, Канада) — для остальных ~250 стран из `COUNTRIES` в `golosovania/karta/index.html`
  координаты ещё не подбирались. Алгоритм подбора (описан выше: географическая доля bbox +
  локальный поиск с проверкой `isPointInFill`/clearance) можно применить к каждой, но это
  разовая ручная/полуавтоматическая работа, ещё не начатая.
- Как рисовать сам бейдж технически — решили, что разумнее как `<image>`+`<text>` ПРЯМО ВНУТРИ
  SVG карты (не HTML-элемент поверх), чтобы он масштабировался вместе с картой при зуме/панорама
  автоматически. Ещё не реализовано (в прототипах бейдж рисовался как `<circle>`+`<text>`
  с эмодзи-сердцем «♥» вместо настоящей картинки — упрощение для скорости прототипирования,
  не финальный вид).
- Страны с несколькими официальными столицами (например, ЮАР — Претория/Кейптаун/Блумфонтейн)
  требуют разового решения, какую точку считать «той самой» — не решено.
- Микрогосударства (Ватикан, Сан-Марино) — сама страна на карте может быть меньше кружка
  независимо от того, куда его поставить; это фундаментальное ограничение любого подхода к
  размещению, не только центра bbox или столицы.
